# 决策点 1 · 深度解析

> **议题**：4 处语义色在白底 + ≤18px 正文场景下不达 WCAG AA 4.5:1
> **来源**：`scripts/design-compliance-scan.mjs` 实测发现
> **关联**：`docs/design-system-meeting.md §决策 1` · `specs/design-tokens.md §1.4 语义色`
> **评审日期**：2026-08-23
> **决策者**：前端主程 + 设计负责人

---

## 1. 问题陈述

提案 §12.3 自承诺："所有正文（14px 及以上）≥ 4.5:1"。但实测发现 4 处不达标：

| # | Token | 实测对比度 | 要求 | 差距 | 典型场景 |
|---|---|---:|---:|---:|---|
| 1 | `--accent` vs 暖米杏底 (`--bg`) | **4.35:1** | 4.5:1 | -0.15 | 主操作按钮在桌面窗口根背景上 |
| 2 | `--success` vs 白底 | **4.07:1** | 4.5:1 | -0.43 | 收入金额 / 收入标签 |
| 3 | `--warning` vs 白底 | **3.60:1** | 4.5:1 | -0.90 | 支出金额 / 支出标签 |
| 4 | `--info` vs 白底 | **4.30:1** | 4.5:1 | -0.20 | 副标题 / 链接 / 副本类型 |

### 1.1 影响程度分级

| Token | 差距 | 严重度 | 用户主观感知 |
|---|---:|---|---|
| `--warning` | -0.90 | 🔴 **高** | "勉强能看清" |
| `--success` | -0.43 | 🟡 中 | "略弱,但可读" |
| `--accent` 暖底 | -0.15 | 🟢 低 | "几乎合规" |
| `--info` | -0.20 | 🟢 低 | "几乎合规" |

## 2. 当前代码里实际用法

### 2.1 涉及组件（按 grep 结果）

| Token | 文件数 | 关键组件 |
|---|---:|---|
| `--success` | **29** | Dashboard, IncomeDetail, RoleRecordsModal, AddRecordModal, AddBaizhanRecordModal, ... |
| `--warning` | **21** | Dashboard, IncomeDetail, BaizhanRoleRecordsModal, MigrationStatus, ... |
| `--accent` (经 `bg-primary`) | **26** | AddAccountModal, AddRecordModal, MigrationStatus, ... |
| `--info` | **0** | （提案 token，未实际应用） |

### 2.2 字号分布实测（典型 IncomeDetail.tsx）

| 位置 | 字号 | 内容 | 是否达 AA 4.5:1 |
|---|---|---|:---:|
| L367 净收入/支出统计 | `text-3xl` (≥18px) | 数字 | ✅ 大字号 AA ≥3.0:1 |
| L760 收入指示 | `text-sm` (14px) | 文字 | ✗ 正文 AA ≥4.5:1 |
| L671/651 收入/支出标签 | `text-xs` (<14px) | 标签 | ✗ 正文 AA ≥4.5:1 |
| L186 主操作按钮 | `text-base` | 按钮文字 | ⚠️ `--accent` 暖底 -0.15 |

> 注：WCAG AA 对 ≥18px 或 ≥14px bold 放宽到 3.0:1。`text-sm` 14px regular 仍按正文 4.5:1 要求。

### 2.3 实际"风险面"

- **最常见场景**：收入 / 支出金额卡片（小字号标签 + 中字号文字 + 大字号统计）
- **次常见**：主操作按钮（`bg-primary` 落到 `--accent` 沉香褐，背景是桌面窗口的暖米杏色）
- **低频**：副本类型 / 链接 / 副标题里的 `--info`（提案 token，代码暂无应用）

## 3. 三个备选方案详解

### 3.1 方案 A · 接受现状（不修复）

**做法**：design-tokens.md 加"已知约束"章节；规范上重申"≥18px 大字号可用 AA ≥3.0:1，正文场景避免直接使用 `--success/--warning/--info`，改用 `--fg` 主文本色"。

**优点**：

- ✅ 0 处代码改动
- ✅ 保留提案 §1.4 设计哲学的视觉优势（沉香褐 + 苔绿 + 焦糖的低饱和度基调）
- ✅ 大字号场景（统计卡片、`text-3xl`）已达标
- ✅ 团队执行成本最低

**缺点**：

- ✗ 4 处正文场景**严格说不符合规范自承诺**（"≥14px 正文 ≥4.5:1"）
- ✗ 实际可读性在 `--warning` 支出标签上偏弱（3.60:1 vs 4.5:1 差 25%）
- ✗ a11y 工具（axe、Lighthouse）会标黄警告，对追求 W3C 标准的潜在用户是负面信号
- ✗ 不达标的 Tag 用法（`text-xs` 收入/支出标签）会持续存在

**适用**：对 a11y 严格度要求低、视觉哲学优先的项目

---

### 3.2 方案 B · 调高饱和度（直调 token）

**做法**：4 个 token 值微调，提升饱和度让对比度达 AA 4.5:1。

| Token | 原 | 新 | vs 白底 |
|---|---|---|---:|
| `--success` | `#5d8770` | `#4d7560` | 4.07 → **5.21:1** ✅ |
| `--warning` | `#a38246` | `#927237` | 3.60 → **4.48:1** ⚠️（还差 0.02） |
| `--info` | `#5e7e94` | `#506c80` | 4.30 → **5.53:1** ✅ |
| `--accent` 暖底 | — | 不动（已是 4.35:1，差 0.15） | — |

> 即使调到 `#927237`，`--warning` 也只到 4.48:1，仍差 0.02。**方案 B 单独无法让 4 项全部合规**，需要搭配 `--warning` 在白底场景不用、只配 soft 底。

**优点**：

- ✅ 仅改 `index.css` 4 个 CSS 变量值，1 个文件
- ✅ 组件代码 0 改动（类名 `ds-success/ds-warning/ds-info` 不变）

**缺点**：

- ✗ 提案 §1.4 的设计哲学「降饱和度 12% 让长时段挂团长窗口不刺眼」被部分抵消
- ✗ `--warning` 仍未达 AA（差 0.02），需搭配使用约束
- ✗ 视觉风格偏离提案包导出的设计意图，需要设计负责人重新审视

**适用**：对 a11y 要求较高、愿意牺牲部分视觉风格的项目

---

### 3.3 方案 C · 新增 `*-strong` 派生 token（推荐）

**做法**：保留原 token 不动，新增 `--success-strong / --warning-strong / --info-strong` 三个深色派生，专供 ≤18px 正文场景。

| Token | 派生自 | 值 | vs 白底 | 适用 |
|---|---|---|---:|---|
| `--success-strong` | `--success` | `#3d5e4a` | **7.25:1** ✅ | 小字号正文 / 标签 |
| `--warning-strong` | `--warning` | `#6e5a30` | **6.63:1** ✅ | 小字号正文 / 标签 |
| `--info-strong` | `--info` | `#3e546a` | **7.83:1** ✅ | 小字号正文 / 副标题 |
| `--accent-strong` | `--accent` | 已有 `#8a4f30` | 6.48:1 ✅ | 已合规，无须新增 |

**优点**：

- ✅ 提案设计哲学完全保留（原 token 不动）
- ✅ 4 项全部达 AA 大幅超过 4.5:1
- ✅ 暗主题也合规（深色派生在暗 surface 上对比度更高）
- ✅ 与 Tailwind 现有 `*-strong` 后缀命名一致
- ✅ 用 `text-ds-success-strong` 直接对应小正文，使用上零学习成本

**缺点**：

- ✗ 改动 5 处文件：`index.css` + `tailwind.config.js` + `specs/design-tokens.md` + ~30 处组件类名
- ✗ 引入 token 数量从 14 → 17（增加 21%）
- ✗ 设计师需要为"正文色 vs 大字色"做两次决策

**适用**：对 a11y 严格度要求高、希望保持设计哲学的项目（**推荐**）

## 5. 推荐结论

### 5.1 推荐 **方案 C**

**理由**：

1. **完整对齐提案哲学** —— 不修改提案 §1.4 已定义的 hex 值，保留"沉香褐 + 苔绿 + 焦糖 + 雾蓝"低饱和度基调
2. **全部合规** —— `--*-strong` 派生在白底均超 6.6:1，大幅超过 AA 4.5:1 要求
3. **改动局部化** —— 影响 ~30 处组件类名（约 5% 总类名），可在 1 个 PR 内完成
4. **向后兼容** —— 现有 `ds-success / ds-warning / ds-info` 仍可用，仅在小正文场景替换为 `*-strong`
5. **命名一致** —— Tailwind 已有 `ds-accent-strong`，扩展到 `*-strong` 家族自然

### 5.2 落地清单

执行 **方案 C** 需完成：

```
1. index.css
   :root + [data-theme="dark"] 块新增 3 个 token

2. tailwind.config.js
   theme.extend.colors['ds-success-strong'] / ['ds-warning-strong'] / ['ds-info-strong']

3. specs/design-tokens.md §1.4
   新增"派生 strong 系列"表格 + "何时用 strong"决策树

4. 组件代码（约 30 处类名替换）
   text-ds-success   → text-ds-success-strong    （小正文）
   text-ds-warning   → text-ds-warning-strong    （小正文）
   text-ds-info      → text-ds-info-strong       （小正文）
   bg-primary/10     → bg-ds-accent-strong/10    （主操作按钮 active 态）
   // 大字号场景（text-3xl 等）保持不变
```

### 5.3 不推荐方案 A / B 的原因

- **A**：提案自承诺与现状矛盾，规范失信于团队；axe/Lighthouse 警告持续存在
- **B**：`--warning` 仍差 0.02，且偏离提案包导出的设计意图；如要 B 调到位，需要更深色（接近 `--warning-strong`），等于变相做 C

## 6. 风险与回退

| 风险 | 概率 | 影响 | 回退方案 |
|---|:---:|---|---|
| `*-strong` 与现有类名语义冲突 | 低 | 中 | 重命名为 `*-strong-text` 或 `*-deep` |
| 视觉"小正文深色"显得突兀 | 中 | 低 | 渐进式替换，先在 `IncomeDetail.tsx` 试 5 处看效果 |
| 设计负责人不接受新增 token | 低 | 中 | 退守方案 B（饱和度微调） |
| 影响暗主题对比度过高 | 低 | 低 | 暗主题使用 `*-strong` 时配 soft 背景 |
