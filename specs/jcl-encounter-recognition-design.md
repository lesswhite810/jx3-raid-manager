# JCL 首领识别：统一战斗状态机与最小身份数据

> 状态：🚧 部分实现 · 全副本单份解析与聚类规则及通用伤害 + 精确 10 金补漏已实现并通过当前离线回归；v6 师徒正向判定已撤回，旧 v7 结果保留为历史。v8 缓存仅存强证据，金额补漏独立重读并以临时结果参与聚类。跨文件三态状态机、Unknown UI 与既有 records 迁移仍未实施。当前 `is_kill=false` 表示未自动确认击杀，不代表新增 Unknown UI。
> 日期：2026-10-31。本文依据现有源码及 2026-10-29 的九份洛阳之战 JCL；不修改游戏日志、正式数据库或已确认记录。

## 1. 结论与硬约束

推荐采用“统一战斗状态机 + 明确证据 + 最小身份数据”，不把判断流程搬进一个庞大的副本配置系统。

1. 全胜成就消息不参与任何成功、失败或置信判断。增加、删除、重复该消息，识别结果必须相同；不能用它训练规则或作为测试唯一真值。
2. 脱战、离场、朝向、满血、战斗时长、侠义、成就、师徒消息和后续开怪不能单独证明首领成功。多个弱信号堆叠也不能自动升级为确认成功。只有同一有效尝试中的同角色有效伤害与精确 10 金，且通过全局关联时间窗、身份和尝试完整性门控，才作为保守正向补漏；强证据优先。金额不足时不裁剪或近似到 10 金。
3. 不在算法中按副本名、首领名、固定 MapID 写专用条件。
4. 同一首领战斗不能因文件名写逐焰或寂夜而采用不同的完成条件。
5. 既有五次成功审计标签不能作为击杀证据；仅采纳可验证的正向条件，不为凑到既有次数而放宽判断。MY 进度仅作旁证，不作为权威完成依据。证据缺失时允许输出待确认，不强迫每份 JCL 二选一。

## 4. 哪些属于算法，哪些属于数据

固定在公共算法中的内容：JCL 事件字段语义、当前战斗边界、运行时实体追踪、重复事件处理、成功与重置证据的先后关系、证据冲突、三态结果、缓存失效、聚类及 CD 传播。用户不配置死亡事件编号、朝向值、秒数阈值、正则或任意布尔公式。

最小身份资料只表达游戏事实：已有的副本/Boss ID；在确有必要且已验证时补充 NPC 模板与首领对应关系、一个首领进度包含哪些实体、特殊宝箱归属。不能把同场出现的所有 NPC 自动归为必须击败的成员；小怪、幻影、阶段实体与独立首领不能仅凭共现推断。无法确定的关联保持未知。

首版不新增规则编辑器。身份资料由一个后端预置源维护，避免前后端各维护一份；后端通过现有配置加载入口提供有效资料。后续只有出现实际维护需求才提供受约束的编辑能力。

名称匹配建议优先精确模板身份；否则在当前已确定副本内先按完整名称直接匹配。作为宝箱匹配小修复，此规则已通用落地：所有副本在无直接命中时，会对双方完整名称去掉中点“·”或英文句点“.”后再匹配，仅唯一候选才归属，直接命中优先；不做双向 contains。伤害 + 精确 10 金补漏由通用算法处理，不按副本名或首领名特判；v8 解析缓存只缓存强证据。

## 5. 统一处理流程

JCL 解码 → 规范化事件 → 实体身份解析 → 战斗尝试重建 → 收集与绑定证据 → 得出结果 → 聚类及记录。

### 5.1 规范化事件与实体

- 保存文件及原行号、事件时间、客户端顺序、事件类型、NPC runtime ID 和模板 ID。
- type 28 表示目标死亡通知，type 9 的零血是候选死亡证据；两者都必须绑定已确认的首领实体及该次战斗，不能算玩家、小怪或任意同名 NPC 的死亡。
- type 8 是 NPC 信息；192 是朝向。不能把 NPC_INFO 的重复出现直接称为新生成，也不能把无名 type 12 物件直接称为首领宝箱。
- 文件名只提供候选身份和索引，不决定成功；配置中的业务 Boss ID 与 NPC 模板 ID 是不同命名空间。
- 全胜成就事件从结果计算输入中排除，原始文件仍可用于人工查看。

### 5.2 战斗尝试与时间边界

- 一份文件可以不完整；多个连续文件也可能属于同一场尝试。先根据实际战斗开始/结束及实体事件重建尝试，再聚类首领进度。
- 按账号、场景及可验证的会话边界隔离；runtime ID 仅在其会话中有效。MapID 相同、时间接近不等于副本实例相同，现有两小时阈值只作分段提示。
- 保留死亡、复活、离场和再次参战的顺序，不能将某个较早阶段的死亡永久锁为整场成功。
- 尚未结束的日志标记为进行中；缺头、截断、跨会话或时间矛盾标记为不完整。暂缺证据不等于拉脱。
- 宝箱或明确结算事件可能出现在战斗结束后，因此不能一律要求在全局战斗 active 内。需要同一会话、唯一对应首领、事件先后关系以及下一次战斗边界来归属；无法确定归属则待确认，不能只用“结束后 N 秒”强行匹配。

### 5.3 证据与决策

| 观察 | 用途 | 限制 |
| --- | --- | --- |
| 确认首领实体死亡/零血 | 候选成功证据 | 必须区分主实体、必要成员与阶段实体；若后续继续战斗或恢复，不能结束整场 |
| 对应首领宝箱首次有效出现 | 候选成功证据 | 唯一归属、首领确实参战；排除战斗前已有宝箱、重复 NPC_INFO、旧场景实体。中途加入或日志缺头导致无法排除旧箱时保持未知 |
| 可直接关联首领的服务器结算/掉落事件 | 未来候选成功证据 | 只有找到真实字段并验证可重复性后才接入，当前不假设该事件已存在 |
| 首领重新恢复并开战 | 重置或新尝试证据 | 先排除阶段切换、新实例和会话不明；证据不足只记“发现再次参战” |
| 全局/首领脱战、离场、满血 | 边界与过程信息 | 不能单独或简单叠加为成功；本批成功场次也出现满血脱战 |
| 同角色有效伤害 + 精确 10 金 | 保守正向补漏 | 同一完整有效尝试内有效伤害达标，10 金位于 JCL 结束前后 15 秒；此窗口不围绕最后一击计算。配置首领名与 type 8 真实名称精确匹配，唯一 runtime、单一 start/end、UID 与尝试完整性门控通过；无治疗导致的 HP 变化或重入，且 Σ13 == max。强证据优先，金额不足不裁剪；MY 仅作旁证 |
| 侠义、成就、师徒消息；朝向 192、团员生还、未再开怪、打下个 Boss | 无关消息或诊断上下文 | 不作为击杀依据；不得按副本名或首领名设例外 |

**上一轮 v5 已实现：单份 `analyze_jcl` 的全副本通用 A/B 击杀规则**。算法不按副本名、MapID 或 BossID 前缀分支。

- **A：单实体路径**：对应的首领专属宝箱可确认；或同模板绑定的同一 `dwID` 先以 `bFight=true` 参战，再出现该实体最后有效的 type 28 死亡或 HP=0。若已有终局死亡后，同一 `dwID` 出现 `bFight=false` 且正 HP，则撤销本轮死亡证据；之后需新的 `bFight=true` 才可重新确认。死亡前普通脱战不单独推断新战斗。
- **B：配置实体与文件实体路径**：先确认配置首领曾参战；其对应宝箱可确认，宝箱身份与归属按“曾参战”标记判断。否则，只有文件实体与配置首领是不同 `dwID` 且双方各自满足 A 的参战与最终死亡/HP=0 证据，才确认击杀；相同 `dwID` 的别名按单实体处理。死亡证据按当前战斗 epoch 配对。

**v6 师徒消息推断已撤回；通用伤害 + 精确 10 金补漏已实现**：师徒、全胜成就与侠义消息不作证据。首领专属宝箱和有效死亡/HP=0等强证据优先。补漏要求同一有效尝试、同角色有效伤害、精确 10 金在全局 ±15 秒关联窗内对应，以及身份和尝试完整性门控通过；配置首领名与 type 8 真实名称精确匹配，唯一 runtime、单一 start/end、UID 有效，无治疗导致的 HP 变化或重入，且 Σ13 == max。金额不足不裁剪。MY 进度只作旁证，不新增 MY 实时监测或采集，也不作为权威判定；真实 MY 开战时复用既有 ImportRecentLogs 最近 1 秒输入后再写 type 1，候选纳入该 1 秒 prefix 并受 epoch/client_ms 门控。只读核对 SQLite 中 quoted/raw ChatInfo UID。该规则全局适用，不使用副本特判；±15 秒是按当前样本验证选定的关联窗，不宣称为所有日志结算延迟的普适规律。v8 仅缓存强证据，缓存命中且 strong=false 时仍独立重读 JCL，金额补漏只生成临时 effective map 参与聚类。已通过最终原件与历史离线回归。

- 脱战、离场、192 朝向、全胜成就不构成正向击杀证据。同名其他实体只有明确 `bFight=true` 时可保守否决；裸正 HP 不能否决，也不能把不同 `dwID` 的正向证据拼接。

已实现的 v7 缓存行为及历史差异见第 7 节。本轮 v8 规则的缓存细节见下文；单份解析规则不表示跨文件三态状态机、Unknown UI 或历史 records 迁移已实施。

每次战斗输出 Completed（已确认完成）、Reset（有充分重置证据）、Unknown（证据不足或冲突），另保留 active/ended/incomplete 阶段。未识别到首领的小怪事件不生成首领结果。

只在已解析身份、战斗边界可用、正向证据满足且无未解决冲突时输出 Completed。多实体首领依据已验证的成员关系判断；不能一方死亡就当然认定整组成功。存在首领专属宝箱时，可直接支撑该首领进度的完成，不要求所有实体都产生死亡事件。

Unknown 不自动写入 bossIds，不触发全通或占用相应 Boss CD；保留证据与中文原因，例如“战斗已结束，缺少可确认完成的事件”。它与 Reset 的显示、统计和后续复核必须区分。

## 6. 聚类、缓存与历史数据

- 【已单独实现】所有副本聚类只汇总已确认击杀；删除“名称不同就取最后一份作击杀”的推断职责。完整跨文件三态中 Unknown 不得在聚类或记录层被兜底升级的约束仍待实现。

本次已实现范围止于聚类结果生成：不实施现有 records 迁移或自动清理。既有复核在没有新聚类实例、或为保留原有经济数据时，可能保留或恢复旧 bossIds，因此重新扫描不保证纠正已保存的历史进度。本轮历史 JCL 回归只离线运行，不写入 live DB；原有经济数据保留逻辑不变。

- 后续成功不能反向将较早拉脱改成成功；后续再次参战也不能不经实例/阶段判别就推翻既有强证据。保留每次尝试与结果依据。
- 缓存使用通用引擎版本、身份资料摘要及源文件指纹。若缓存的是跨文件最终结果，必须包含所有依赖文件/邻接边界指纹；相邻文件变化要失效相关尝试。更合适的是缓存单文件规范化事件或证据，再按会话重算结果。
- 持久结果要显式保存 outcome、reason、证据位置和版本。现有 is_kill 不能用 -1 表示 Unknown，因为读取代码将任何非零值视为 true。
- 【v7 历史实现】单份 JCL 解析缓存曾使 v6 及更早解析缓存下次扫描时失效并重算。
- 【本轮 v8 已实现】SQLite 只缓存 JCL 强证据结果，不缓存金额补漏；即使命中缓存，只要 strong=false 就独立重读 JCL 并重建候选。金额补漏通过临时 effective map 参与聚类，不写回 strong 缓存。跨文件结果缓存的身份摘要及相邻文件依赖仍按本节方案处理。
- 已确认/已拒绝记录默认不自动改写。扫描中及待确认自动记录可基于新结果更新，但必须明确处理“全部变成 Unknown、没有可聚类实例”的旧记录，不能因没有新实例而遗漏旧错误 bossIds，也不能删除工资和掉落。
- 历史重算先给差异预览及来源，保留人工确认/人工编辑优先级；只更新确定属于自动推断的字段。

## 7. 历史兼容与实施顺序

1. 先实现事件与身份层、统一战斗尝试和解释性结果。在独立回放中运行，不立即改历史业务记录。
2. 单份 `analyze_jcl` 中此前洛阳专用的两处击杀判定已改为全副本通用证据规则，不再依赖副本名、MapID 或 BossID 前缀；成就消息无关性与名称标准化冲突测试用于约束该通用规则。
3. 用完整原始日志验证新引擎，不只用当前精简 fixture；新方案如依赖此前未保留的事件，需要重新提取和脱敏样本。
4. 上一轮 v5 已完成对 4,293 份已解析非洛阳样本的逐字段比较；v6 实验结果已撤回。本轮 v7 历史回放见下文；通用伤害 + 精确 10 金补漏的最终回归结果见 v8 小节。
5. 以影子运行记录差异；未完成验证的历史输入暂由旧入口处理，必须标明旧推断来源，不能把旧 true 当作新引擎的强证据。这是迁移安排，不是长期允许用户开启弱信号判杀的配置项。

## 9. 当前设计边界

现有 JCL 不一定包含足以区分脚本结算成功与普通脱战的信息。师徒通知、全胜成就、侠义及未与有效伤害关联的普通奖励和武林通鉴语句均不单独作击杀依据。首领专属宝箱及有效死亡/HP=0等强证据优先；同角色有效伤害与精确 10 金仅在全局 ±15 秒关联窗、身份及尝试完整性门控通过时作保守补漏，金额不足不裁剪。配置名称与 type 8 真实名称、唯一 runtime、单 start/end、UID、无治疗 HP 变化或重入及 Σ13 == max 均须成立。MY 进度只作旁证，不新增实时监测或权威判定。该规则全局统一，不按副本特判。本轮规则实现及离线回归已完成；跨文件三态、Unknown UI 与既有 records 迁移仍未实施。
